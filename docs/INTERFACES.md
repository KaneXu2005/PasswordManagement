# API and vault format

## Storage API

```python
from storage import initialize_vault, load_vault, save_vault

initialize_vault(path, master_password)      # -> None
entries = load_vault(path, master_password) # -> list[dict[str, str]]
save_vault(path, master_password, entries)  # -> None
```

- `path` is a string or `pathlib.Path`. Its parent directory must exist.
- `master_password` is non-empty UTF-8 text; callers must not strip or normalize it.
- Initialization creates an encrypted empty list and refuses to overwrite any
  existing target. Loading verifies the password, derives the key, authenticates
  the data and returns a complete entry list only on success.
- Saving authenticates the existing vault before replacing the complete list.
  It does not merge entries, create a missing vault or change the master password.
- Each save uses a new nonce. Callers must serialize read-modify-write operations;
  there is no concurrent-writer conflict detection or persistent unlock session.
- Only entry data crosses this API. Derived keys are not returned to callers or
  persisted. Callers must not handle errors by clearing or reinitializing a vault.

## Entry and account operations

```json
[
  {"site": "github", "username": "alice", "password": "example-only-password"}
]
```

Entries form a list, possibly empty. Each entry has exactly these three non-empty
UTF-8 string fields. Site and username cannot be whitespace-only. Sites are unique
and case-sensitive; values, including password spaces, are preserved. Additional
fields and multiple accounts for one site are not supported by version 1.

`entries.py` exposes:

| Function | Result |
| --- | --- |
| `add_entry(entries, site, username, password)` | New complete list; duplicate sites are rejected. |
| `list_entries(entries)` | Site/username summaries sorted by site, with no passwords. |
| `get_entry(entries, site)` | Detached copy of the selected complete entry. |
| `delete_entry(entries, site)` | New list without the selected entry. |

These operations do not mutate their inputs or access files. They share
`crypto.validate_entries` for structural validation. Missing get/delete targets
raise `entries.EntryNotFoundError`, a `VaultError` subclass.

`generator.generate_password(length=20)` returns a string of 12-1024 characters
with lowercase, uppercase, digits and symbols. Invalid lengths raise `ValueError`.

## Errors and CLI exit status

Expected vault errors inherit `errors.VaultError`:

| Exception | Meaning |
| --- | --- |
| `InvalidMasterPassword` | Password does not match the stored verifier, which may itself have been modified. |
| `VaultIntegrityError` | AES-GCM authentication failed; no plaintext is returned. |
| `VaultFormatError` | Malformed file, changed encoding, unsupported fields/version/parameters or invalid Base64. |
| `VaultAlreadyExistsError` | Initialization target already exists. |
| `VaultNotFoundError` | Requested vault does not exist. |
| `VaultIOError` | File read/write failed, or publication succeeded but temporary-file cleanup failed. |
| `EntryValidationError` | Invalid entries or encrypted output exceeding the file size limit. |

Invalid master-password arguments raise `ValueError`. CLI failures print a clear
message to standard error and exit 1; invalid command arguments exit 2, Ctrl+C
exits 130 and success exits 0. If cleanup fails after publication, the message
includes `Vault was saved`; callers must display that distinction accurately.

## Version 1 file format

The following illustrates the fields; actual file bytes are generated by storage:

```json
{
  "ciphertext": "<Base64: ciphertext followed by 16-byte GCM tag>",
  "kdf": {
    "length": 32,
    "memory_cost": 65536,
    "name": "argon2id",
    "parallelism": 4,
    "salt": "<Base64: 16 random bytes>",
    "time_cost": 3,
    "version": 19
  },
  "master_hash": "$argon2id$v=19$m=65536,t=3,p=4$...$...",
  "nonce": "<Base64: 12 random bytes>",
  "version": 1
}
```

The verifier has its own library-generated salt. The key-derivation salt is
independent and public. Argon2id produces a 32-byte AES-256 key from the master
password and KDF salt, never from the stored verifier.

`version`, `master_hash` and `kdf` are authenticated as AAD using sorted-key,
compact UTF-8 JSON. The complete file has a single accepted representation:
UTF-8, sorted keys, two-space indentation and one final newline. Format checks
reject edits only to whitespace, key order or escapes; AES-GCM authenticates the
protected values and ciphertext. Formatting checks are not a substitute for GCM.

The reader rejects duplicate or unknown fields, invalid Base64, files larger than
16 MiB and unsupported versions or Argon2id parameters. Parameter changes require
an explicit version/migration design.

Saving writes encrypted content to a same-directory temporary file, flushes and
syncs it, then atomically replaces the old file. Initialization uses atomic
hard-link publication so a competing existing file cannot be overwritten. POSIX
files are created with mode 0600. Cleanup normally removes temporary files; a
cleanup error preserves the original save error or reports successful publication.
